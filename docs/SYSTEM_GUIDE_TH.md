# คู่มือการทำงานของระบบ PDH Smart EMS Command & Refer

ฉบับ 1.0 | วันที่ 25 กันยายน 2569 | อ้างอิงโค้ดหลังพัฒนา AUTH-1

สำหรับเจ้าหน้าที่ศูนย์สั่งการ เจ้าหน้าที่ส่งต่อ พลขับ ผู้ดูแลระบบ และผู้พัฒนา

## 1. วัตถุประสงค์และสถานะระบบ

ระบบช่วยจัดการภารกิจ EMS และการส่งต่อ ตั้งแต่สร้างงาน จัดรถและทีม ยืนยันความพร้อม ติดตามการเดินทาง ส่งมอบ ณ ปลายทาง กลับฐาน และสรุปรายงาน โดยใช้บัญชีผู้ใช้และระบบเข้าสู่ระบบส่วนกลาง

คู่มือนี้อธิบายความสามารถที่พบในโค้ดปัจจุบัน ไม่ใช่เอกสารรับรองความพร้อมใช้งานจริง ทั้งระบบยังต้องพัฒนา permission และการตรวจว่าผู้ใช้ได้รับมอบหมายภารกิจนั้นจริงใน AUTH-2 ก่อนเปิดใช้งาน production

| ส่วนงาน | สถานะปัจจุบัน |
| --- | --- |
| Login/Logout และ session ฝั่งเซิร์ฟเวอร์ | พัฒนาและทดสอบ AUTH-1 แล้ว |
| แผนที่ ภารกิจ Driver Cab และรายงาน | มีหน้าจอและ API; ผ่าน regression ตามรายงาน AUTH-1 |
| การตรวจ role เดิม | มีบาง endpoint; ยังไม่ครอบคลุม permission และสิทธิ์ระดับรายการ |
| เมนูตามผู้ใช้ | เซิร์ฟเวอร์ส่งรายการเมนูตาม role เดิม; ไม่ใช่ขอบเขตความปลอดภัยของ API |
| จัดการ users/roles/permissions ผ่าน Admin Back Office | ยังไม่เปิดใช้งาน; เป็นขอบเขต AUTH-2/3 |
| Audit | มีตารางและบันทึกเหตุการณ์; ยังไม่มีหน้าจอตรวจสอบกลางครบชุด |
| Security Events และการจัดการ session รายอุปกรณ์ | มีโครงสร้างบางส่วน; ยังไม่ใช่ระบบจัดการที่สมบูรณ์ |

## 2. ภาพรวมการทำงาน

ลำดับข้อมูลหลัก:

```text
ผู้ใช้บนมือถือ / Tablet / Desktop
             ↓
หน้าเว็บ React และระบบ Login กลาง
             ↓  Cookie + การตรวจคำขอ
Express API → ตรวจ session / สถานะบัญชี / role ที่ใช้อยู่
             ↓
บริการภารกิจ / แผนที่ / รถ / สถานพยาบาล / รายงาน
             ↓
MariaDB → ข้อมูลปฏิบัติงาน / sessions / audit_logs
```

การซ่อนเมนูช่วยให้ใช้งานสะดวก แต่การอนุญาตให้แก้ข้อมูลต้องเกิดที่ API ด้วย ปัจจุบันการจำกัดข้อมูลเฉพาะภารกิจของผู้ใช้ยังเป็นงานที่ต้องทำต่อ

| หน้าจอ | การใช้งานหลัก |
| --- | --- |
| Login | เข้าสู่ระบบด้วย username หรือรหัสบุคลากร |
| แผนที่สั่งการ | ดูรถ ฐาน สถานพยาบาล ภารกิจ และสถานะ GPS |
| ภารกิจ Refer / EMS | สร้าง/จัดรถและทีม ตรวจความพร้อม และติดตามสถานะ |
| Driver Cab | แสดงข้อมูลการเดินทางและดำเนินขั้นตอนภารกิจ |
| โรงพยาบาล/ปลายทาง | จัดการข้อมูลสถานพยาบาลตามสิทธิ์เดิม |
| ฐานกู้ชีพ | จัดการข้อมูลฐานและพิกัดตามสิทธิ์เดิม |
| รายงาน & KPIs | สรุปภารกิจ เวลา ระยะทาง และข้อมูลเชิงพื้นที่ |
| แถบบัญชี | ดูชื่อและ role เปลี่ยนรหัสผ่าน และออกจากระบบ |

## 3. การเข้าสู่ระบบและบัญชีผู้ใช้

### 3.1 เข้าสู่ระบบ

1. เปิด URL ระบบที่ผู้ดูแลแจ้ง หรือเส้นทาง /login
2. กรอก username หรือรหัสบุคลากรที่ผูกกับบัญชี พร้อมรหัสผ่าน
3. เลือก “จดจำการเข้าสู่ระบบ” เฉพาะอุปกรณ์ส่วนตัว
4. กด “เข้าสู่ระบบ” และตรวจชื่อ/role บนแถบบัญชีก่อนเริ่มงาน
5. หากระบบกำหนดให้เปลี่ยนรหัสผ่าน ต้องดำเนินการก่อนเข้าใช้งานส่วนอื่น

ข้อความแจ้งเข้าสู่ระบบไม่สำเร็จอาจหมายถึงข้อมูลไม่ถูกต้อง บัญชีไม่พร้อมใช้งาน หรือถูกล็อก ระบบไม่เปิดเผยว่ารหัสผู้ใช้มีอยู่หรือไม่

การจดจำการเข้าสู่ระบบไม่ได้ยกเลิกเวลาหมดอายุของ session และไม่ได้บันทึกรหัสผ่านไว้ใน localStorage

### 3.2 เปลี่ยนรหัสผ่าน

1. เปิด “เปลี่ยนรหัสผ่าน” ที่แถบบัญชี
2. กรอกรหัสผ่านปัจจุบัน รหัสผ่านใหม่ และยืนยันรหัสผ่านใหม่
3. กดบันทึก เมื่อสำเร็จให้เข้าสู่ระบบใหม่

ค่าเริ่มต้นกำหนดความยาวรหัสใหม่อย่างน้อย 12 ตัวอักษร และไม่เกิน 72 ไบต์ UTF-8 รหัสใหม่ต้องต่างจากรหัสปัจจุบัน การเปลี่ยนสำเร็จจะยกเลิก session ทุกอุปกรณ์

### 3.3 ออกจากระบบและสลับผู้ใช้

1. ประสานศูนย์สั่งการก่อน หากมีภารกิจที่ยังดำเนินอยู่
2. เลือก “ออกจากระบบ” หรือ “ออกทุกอุปกรณ์” แล้วกดยืนยัน
3. ตรวจว่ากลับมาหน้า Login จึงให้ผู้ใช้อีกคนเข้าสู่ระบบ
4. ตรวจชื่อ/role ของบัญชีใหม่อีกครั้ง

หากระบบแจ้งออกจากระบบไม่สำเร็จ ให้ลองใหม่ อย่าถือว่า session ฝั่งเซิร์ฟเวอร์ถูกยกเลิกแล้ว การปิดหน้าต่างเบราว์เซอร์เพียงอย่างเดียวไม่ใช่การสั่ง Logout

### 3.4 Session และค่าตั้งต้น

| รายการ | ค่าเริ่มต้น | ผลต่อผู้ใช้ |
| --- | --- | --- |
| Idle timeout | 1,800 วินาที (30 นาที) | หมดอายุเมื่อไม่มีคำขอที่ผ่านการยืนยันตัวตนตามช่วงเวลา |
| Absolute lifetime | 43,200 วินาที (12 ชั่วโมง) | ต้องเข้าสู่ระบบใหม่เมื่อครบอายุ แม้ยังมีการใช้งาน |
| จำนวน Login ผิดก่อนล็อกชั่วคราว | 5 ครั้ง | บัญชีถูกพักการเข้าสู่ระบบชั่วคราว |
| ระยะเวลาล็อก | 900 วินาที (15 นาที) | ลองใหม่หลังพ้นระยะ หรือประสานผู้ดูแล |
| Login rate limit | 30 คำขอต่อ IP / 900 วินาที | จำกัดคำขอจำนวนมากจากแหล่งเดียวกัน |

ตัวเลขเปลี่ยนได้จาก configuration การดึงข้อมูลเบื้องหลังนับเป็นคำขอที่อาจต่อ idle timeout ได้ จึงไม่ควรตีความ idle timeout ว่าเป็นเวลานับจากการแตะหน้าจอครั้งสุดท้ายเสมอ

## 4. บทบาทและเมนู

มี role เดิม 8 แบบ ได้แก่ SUPER_ADMIN, EMS_ADMIN, EMS_COMMANDER, REFER_CENTER, DISPATCHER, DRIVER, EMS_STAFF และ VIEWER

| Role | เมนูที่เซิร์ฟเวอร์ส่งใน AUTH-1 |
| --- | --- |
| SUPER_ADMIN / EMS_ADMIN | แผนที่ ภารกิจ Driver Cab สถานพยาบาล ฐาน และรายงาน |
| EMS_COMMANDER / REFER_CENTER / DISPATCHER | แผนที่ ภารกิจ และรายงาน |
| DRIVER | Driver Cab |
| EMS_STAFF | ภารกิจ |
| VIEWER | แผนที่ |

ตารางนี้เป็นพฤติกรรมเมนู ไม่ใช่ permission matrix ที่สมบูรณ์ โดยเฉพาะ VIEWER ยังไม่ควรถูกถือว่าถูกบังคับ read-only ครบทุก API การกำหนดสิทธิ์จากฐานข้อมูลและการตรวจเจ้าของ/ผู้ได้รับมอบหมายภารกิจต้องทำต่อใน AUTH-2

## 5. ขั้นตอนภารกิจส่งต่อ (Refer)

### 5.1 สร้างภารกิจ

1. เปิดหน้าภารกิจและเลือกสร้าง Refer
2. ระบุสถานพยาบาลต้นทางและปลายทาง
3. ตรวจความถูกต้องก่อนบันทึก
4. เก็บเลขภารกิจที่ระบบสร้างไว้ใช้ประสานงาน

เมื่อสร้างสำเร็จ สถานะเริ่มต้นเป็น CREATED

### 5.2 จัดรถ พลขับ และทีม

1. เปิดภารกิจที่ต้องการและเลือกจัดทรัพยากร
2. เลือกรถ พลขับ และสมาชิกทีมที่พร้อม
3. ตรวจว่าทรัพยากรไม่ติดภารกิจอื่น แล้วบันทึก
4. ยืนยันความเข้าใจตรงกันระหว่างศูนย์สั่งการ พลขับ และทีม

ระบบตรวจข้อมูล active สถานะรถ/บุคลากร และการซ้อนภารกิจตามเงื่อนไขที่มีใน controller หากได้รับข้อผิดพลาด 409 ให้ตรวจการใช้งานทรัพยากรปัจจุบันก่อนจัดใหม่ เมื่อจัดสำเร็จภารกิจเป็น ASSIGNED

### 5.3 ยืนยันความพร้อมและตรวจรถก่อนออก

1. พลขับยืนยันความพร้อม
2. ทีมยืนยันความพร้อม
3. ทำรายการตรวจรถก่อนออก (Pre-trip) ตามข้อเท็จจริง
4. ตรวจผลผ่าน/ไม่ผ่าน หากไม่ผ่านให้แก้สาเหตุก่อนดำเนินการต่อ

รายการในระบบครอบคลุมน้ำมัน ออกซิเจน อุปกรณ์ทางการแพทย์ ไฟ/ไซเรน ยาง/เบรก การสื่อสาร และกล้อง/GPS เกณฑ์ในโค้ดเป็นการตรวจของซอฟต์แวร์ ต้องให้หน่วยงานทบทวนเทียบกับนโยบายตรวจรถของตนก่อนใช้งานจริง

เมื่อทั้งพลขับและทีมยืนยันแล้วอาจเป็น CREW_CONFIRMED; เมื่อ Pre-trip ผ่านด้วยจะเป็น READY

### 5.4 ออกเดินทางจนปิดงาน

1. กดออกเดินทางหลังตรวจความพร้อม สถานะเปลี่ยนเป็น EN_ROUTE
2. ถึงปลายทางแล้วบันทึกการมาถึง เป็น ARRIVED
3. ส่งมอบและระบุชื่อเจ้าหน้าที่ผู้รับ พร้อมหมายเหตุที่จำเป็น เป็น HANDOVER_COMPLETED
4. เริ่มเดินทางกลับ เป็น RETURNING
5. กลับและตรวจความเรียบร้อยแล้วปิดภารกิจ เป็น COMPLETED

เมื่อปิดภารกิจสำเร็จ โค้ดจะคืนสถานะรถและพลขับเป็น AVAILABLE ควรตรวจรายการในระบบให้ตรงกับความพร้อมจริงก่อนรับงานใหม่

```text
CREATED → ASSIGNED → ยืนยันพลขับ/ทีม + Pre-trip
                            ↓
                          READY
                            ↓
EN_ROUTE → ARRIVED → HANDOVER_COMPLETED → RETURNING → COMPLETED
```

แผนภาพเป็นลำดับปฏิบัติงานที่ควรทำ ไม่ใช่คำยืนยันว่า API ป้องกันการข้ามทุกสถานะแล้ว ปัจจุบันยังต้องตรวจความครบถ้วนของ transition และสิทธิ์การดำเนินการต่อ

### 5.5 Emergency Override

โค้ดรองรับออกเดินทางโดยข้ามความพร้อมบางรายการเมื่อระบุเหตุผล โดยเหตุผลต้องมีอย่างน้อย 5 ตัวอักษรและมีการบันทึกเหตุการณ์ การมีปุ่มนี้ไม่ถือเป็นการให้อำนาจอนุมัติทางปฏิบัติงาน ต้องเป็นไปตามนโยบายของหน่วยงาน และการบังคับ permission ของ override ยังต้องทำให้ครบก่อน production

## 6. ภารกิจฉุกเฉินและการแนะนำรถ

1. เปิดแผนที่สั่งการและระบุตำแหน่งเหตุ
2. ขอรายการรถที่ระบบแนะนำ
3. ตรวจสถานะรถ ความสดใหม่ของ GPS และความพร้อมของทีมกับศูนย์สั่งการ
4. เลือกรถและบันทึก Quick Dispatch ตามหน้าจอ
5. ติดตามภารกิจและบันทึกขั้นตอนปฏิบัติงานต่อ

Quick Dispatch ในโค้ดปัจจุบันสร้างภารกิจเป็น EN_ROUTE และบันทึกเวลาออกเดินทางทันที จึงไม่ใช่ลำดับ CREATED/READY แบบ Refer ต้องทบทวนการตรวจความพร้อมและสิทธิ์ของทางลัดนี้ก่อนใช้งานจริง

ผู้ให้บริการคำนวณเส้นทางปัจจุบันคือ simple_estimate ใช้ระยะเส้นตรงคูณตัวประกอบ 1.35 และประมาณเวลาจากค่าความเร็วที่กำหนดในโค้ด จึงไม่ใช่เส้นทางจราจรจริงหรือการรับประกันเวลาถึง การเลือกหน่วยปฏิบัติการยังต้องอาศัยข้อมูลภาคสนาม

## 7. Driver Cab และ GPS

1. ตรวจชื่อบัญชี รถ และภารกิจก่อนใช้งาน
2. อนุญาตตำแหน่งให้เบราว์เซอร์และตรวจว่าอุปกรณ์รับสัญญาณได้
3. ดูสถานะการเชื่อมต่อ ตำแหน่ง ความเร็ว และจำนวนข้อมูลรอส่ง
4. บันทึกถึงปลายทาง ส่งมอบ กลับ และปิดงานตามสถานการณ์จริง
5. ถ้าข้อมูล GPS ผิดปกติ ให้ยืนยันตำแหน่งกับศูนย์สั่งการผ่านช่องทางที่หน่วยงานกำหนด

โค้ดปัจจุบันส่ง GPS เป็นชุดประมาณทุก 10 วินาที และเก็บจุดรอส่งในเบราว์เซอร์ได้สูงสุด 500 จุด ค่า NORMAL_SYNC_INTERVAL_SEC/EMERGENCY_SYNC_INTERVAL_SEC ในตัวอย่าง environment ยังไม่ควรถูกถือว่าควบคุม timer นี้โดยอัตโนมัติ

ข้อจำกัดที่ต้องทราบ: engine มีการเรียกตำแหน่งจำลองเมื่อ geolocation ใช้ไม่ได้ และหน้า Driver Cab มีส่วนทดสอบความเร็ว ก่อนใช้งานจริงต้องแยกหรือปิดโหมดจำลองให้ชัดเจน ข้อมูลที่เกิดจาก fallback นี้ไม่ควรถูกนำไปยืนยันตำแหน่งจริง

เมื่อ logout, session หมดอายุ หรือเปลี่ยนผู้ใช้ ระบบจะหยุดการติดตามและล้างคิว GPS ของบัญชีเดิมเพื่อป้องกันข้อมูลข้ามบัญชี การเริ่มหน้าเว็บใหม่ก็ล้างคิวเดิมด้วย จึงยังไม่ใช่ระบบกู้คืนข้อมูล offline แบบคงทน หากมีข้อมูลส่งไม่สำเร็จต้องประสานและบันทึกเพื่อกระทบยอดภายหลัง

## 9. เมื่อระบบหรือการเชื่อมต่อมีปัญหา

| อาการ | แนวทางดำเนินการ |
| --- | --- |
| Login ไม่สำเร็จ | ตรวจข้อมูลผู้ใช้/รหัสผ่าน รอเมื่อถูกล็อกหรือจำกัดคำขอ และประสานผู้ดูแล |
| Session หมดอายุ / 401 | เข้าสู่ระบบใหม่ ตรวจชื่อและภารกิจอีกครั้ง |
| 403 | ตรวจข้อความว่าเป็น CSRF, ต้องเปลี่ยนรหัสผ่าน, role หรือเงื่อนไขความพร้อมของภารกิจ |
| 409 เมื่อจัดทรัพยากร | ตรวจรถ/พลขับ/ทีมที่อาจถูกใช้งานในอีกภารกิจ |
| 429 | หยุดส่งคำขอซ้ำ รอตามช่วงเวลาที่กำหนด |
| 503 หรือเชื่อมต่อไม่ได้ | แจ้งผู้ดูแล และใช้วิทยุ/โทรศัพท์ตามแผนปฏิบัติการของหน่วยงาน |
| แผนที่ไม่มีข้อมูล | ตรวจการ Login, API, ฐานข้อมูล และอินเทอร์เน็ต; บางหน้ารับข้อผิดพลาดแล้วแสดงรายการว่าง |
| ตำแหน่งไม่ตรง / ค้าง | ตรวจสิทธิ์ตำแหน่ง สัญญาณ เวลา GPS ล่าสุด และโหมดจำลอง |
| Logout ล้มเหลว | ลองใหม่และอย่าส่งต่ออุปกรณ์โดยถือว่าออกจากระบบสำเร็จแล้ว |

ระหว่างภารกิจ อย่าสร้างงานซ้ำทันทีเมื่อไม่แน่ใจว่าคำขอเดิมสำเร็จหรือไม่ ให้ค้นเลขภารกิจ/ตรวจสถานะกับศูนย์ก่อน ข้อมูลที่บันทึกสำเร็จอยู่บนเซิร์ฟเวอร์ไม่ถูกลบด้วยการ Logout

## 10. การติดตั้งและเริ่มระบบสำหรับผู้ดูแล

แนวทางนี้ใช้กับการพัฒนา/ทดสอบในเครื่อง โครงการใช้ Node.js 20 ใน Dockerfile และ SQL migration ที่ใช้ syntax ของ MariaDB ผล AUTH-1 ทดสอบกับ MariaDB 10.4.32; Docker Compose กำหนด 10.11 ไม่ควรถือว่ารองรับ MySQL 8 ทุก migration โดยไม่ทดสอบ

### 10.1 เตรียม dependency และ configuration

จากโฟลเดอร์โปรเจกต์:

```powershell
npm run install:all
```

ใช้ .env.example เป็นแม่แบบสำหรับ server/.env และกำหนด DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME, CORS_ORIGIN และค่าควบคุม session ตามสภาพแวดล้อมจริง dotenv อ่านจาก working directory; คำสั่ง backend ใน package scripts ทำงานจากโฟลเดอร์ server

อย่าทับ server/.env ที่มีอยู่แล้ว และไม่เก็บรหัสผ่านจริงลง Git สำหรับ Docker Compose ให้กำหนด environment ของ Compose แยกตาม docker-compose.yml

### 10.2 ฐานข้อมูลและ migration

1. เตรียมฐานข้อมูลและบัญชีบริการที่เชื่อมต่อได้
2. สำรองฐานเดิมและทดสอบ restore ลงฐานชื่อใหม่ก่อนเปลี่ยน schema
3. ตรวจชื่อ DB_NAME ให้ตรงฐานเป้าหมาย
4. รัน migration จากโฟลเดอร์ server

```powershell
Set-Location server
npm run migrate
Set-Location ..
```

Migration runner บันทึกชื่อไฟล์ที่ผ่านแล้วใน schema_migrations และล็อกการรันซ้อน SQL DDL อาจ commit แยกจากกัน หากล้มเหลวต้องตรวจ schema ที่เปลี่ยนไปแล้วก่อนรันซ้ำ

คำสั่ง seed มีไว้สำหรับสร้างข้อมูลเริ่มต้น/ข้อมูลทดสอบเท่านั้น และสร้างข้อมูลการปฏิบัติงานตัวอย่างด้วย ไม่ควรใช้เพิ่มบัญชีผู้ใช้บนฐานจริงแทน Admin Back Office ต้องตั้ง SEED_ADMIN_PASSWORD และ SEED_STAFF_PASSWORD ก่อนใช้ และไม่ใช้รหัส fixture ของชุดทดสอบในงานจริง

### 10.3 เปิดระบบพัฒนา

```powershell
npm run dev
```

ค่าเริ่มต้น: หน้าเว็บ http://localhost:5173 และ API http://localhost:5000 โดย Vite proxy เส้นทาง /api ไป backend ตรวจ API ที่ GET /api/health และเปิดหน้า Login ที่ http://localhost:5173/login

health endpoint ส่ง HTTP 200 ได้แม้ database เป็น DISCONNECTED จึงต้องอ่าน body.status และ body.database ร่วมด้วย

### 10.4 Build และ deployment

```powershell
npm run build
```

ก่อน deployment จริง ต้องปิดประเด็น AUTH-2/IDOR, โหมดจำลอง, นโยบายปฏิบัติการ และรายการตรวจ production ให้ครบ จากนั้นจึงกำหนด HTTPS และ CORS_ORIGIN แบบระบุ origin เดียวที่ตรงกับหน้าเว็บ Production cookie มี Secure และไม่ควรใช้งานผ่าน HTTP

ต้อง deploy client/API รุ่นเดียวกัน เพราะ client รุ่น AUTH-1 ไม่ใช้ bearer JWT แล้ว Docker image ไม่รัน migration ให้อัตโนมัติ ต้องจัดลำดับงาน migration เอง คำสั่ง migrate แบบ npm ใช้ tsx; ใน production image ที่ไม่มี devDependencies ให้ใช้ runner ที่ compile แล้วและมีไฟล์ SQL เช่น node dist/db/migrate.js

Behind proxy ต้องตรวจ trusted proxy และการนับ IP; ค่าเริ่มต้นไม่เชื่อ X-Forwarded-For โดยอัตโนมัติ อาจทำให้หลายผู้ใช้ถูกนับเป็น IP ของ proxy เดียวกัน

## 11. การสำรอง กู้คืน และบำรุงรักษา

สิ่งที่ต้องครอบคลุมใน backup ได้แก่ข้อมูลผู้ใช้/สิทธิ์ sessions, audit_logs, security_events และข้อมูลภารกิจ/รถ/บุคลากร ควรเก็บ application version และ configuration สำหรับการกู้คืนควบคู่กัน โดยจำกัดการเข้าถึงไฟล์ backup

มี scripts/backup-db.sh และ scripts/restore-db.sh สำหรับสภาพแวดล้อม Bash/mysql tools ตัวแปรรหัสผ่านของสองสคริปต์นี้ใช้ DB_PASS ซึ่งต่างจาก DB_PASSWORD ของแอป สคริปต์ backup เดิมมี retention 30 วันในโค้ด จึงต้องทบทวนก่อนใช้กับนโยบายเก็บข้อมูลจริง

ลำดับการทดสอบกู้คืน:

1. บันทึกฐานต้นทาง เวลา รุ่นแอป และไฟล์ backup
2. สร้างฐานทดสอบกู้คืนชื่อใหม่
3. Restore ลงฐานใหม่นั้น โดยตรวจปลายทางก่อนยืนยันคำสั่ง
4. เปรียบเทียบจำนวนข้อมูลและความสัมพันธ์ พร้อมตรวจบัญชี/role โดยไม่เผยแพร่ hash หรือข้อมูลอ่อนไหว
5. เปิดแอปในสภาพแวดล้อมแยกและทดสอบ Login/ภารกิจ
6. เก็บผลการทดสอบและผู้รับผิดชอบ

ในงาน AUTH-1 ได้ทดสอบ backup/restore ในเครื่อง และยืนยันว่า ID, username, hash, role และ active flag ของบัญชีเดิม 3 รายการคงเดิมหลัง migration ผลนี้ไม่แทนการซ้อมกู้คืน production
